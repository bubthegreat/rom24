# KBK on Python ROM: Content, Systems & In-Memory Persistence Redesign

**Date:** 2026-07-01 (rev 2 — systems brought into scope, profiles dropped)
**Repos:** `rom24` (engine, this repo) · `kbk` (content source of truth, C mud)
**Status:** Draft for review

## Background

`rom24` ("Pyom") is a Python re-authoring of ROM 2.4. It currently ships stock ROM
content only, loads its game tables from JSON files (`src/data/*.json`), and
persists world state (every mob/object instance) as JSON under `data/world/` —
treating the process like a long-lived VM.

`kbk` is the resurrected KBK mud (Tartarus 1.0, a ROM 2.4 derivative) running in
C: 13 classes, 24 playable races, ~640 skill-table slots, 35 skill groups,
100 area files (96 in the Tartarus OLC `#AREADATA/#MOBDATA/#OBJDATA/#ROOMDATA`
format), plus its own systems: cabals, bounties, quest store, and
item/mob/room programs.

This effort turns rom24 into **KBK running in Python** — KBK's content and
systems on the Python engine — and fixes the persistence design to
**container semantics**: boot pristine from flat files into memory, run, and
reset clean on restart.

## Decisions (agreed in brainstorming)

| # | Decision | Choice |
|---|----------|--------|
| 1 | Success bar | **KBK runs entirely on the Python framework — full parity is the project end state.** Engine loads KBK areas and class/race/skill/group tables; cabals, bounties, quest store, and prog execution are implemented. Individual spell/skill *effects* are ported incrementally behind the stub policy (#6) — stubs are stepping stones, not the finish line |
| 2 | Repo layout | **rom24 becomes the Python KBK mud.** No profile switch — stock ROM content and JSON tables are removed; the ~97 existing Python spell implementations are kept and rewired to KBK's skill table |
| 3 | Conversion | **Repeatable converter** — kbk's C repo stays the source of truth; a tool regenerates rom24's KBK content from it |
| 4 | Persistence | **Players + system files only.** No JSON tables, no world-instance persistence. World is in-memory, rebuilt pristine each boot |
| 5 | Content format | **Defer the modern format.** Extend the `.are` parser now; converting all content to a modern format is a separate future effort |
| 6 | Unimplemented spells | **Visible but inert stubs** — practicable and listed, casting fizzles gracefully with no mana cost and no crash |

## Goals

1. Remove all JSON game-data machinery: table load/save, world-instance
   persistence, pickle legacy loads.
2. Hold all game tables in memory as plain Python modules (KBK's tables,
   generated by the converter).
3. Provide a repeatable converter that regenerates KBK content from the kbk
   C repo (`const.c`, `materials.lst`, `area/*.are`).
4. Teach the area loader KBK's Tartarus OLC format so all 100 KBK areas load.
5. Implement KBK's core systems: cabals, bounties, quest store, and the
   item/mob/room prog trigger framework.
6. Boot end-to-end as KBK: areas load, resets populate the world, progs fire,
   a character can be created with KBK classes/races and play.

## Non-Goals (explicitly out of scope)

- Porting every KBK-specific spell/skill effect up front (stubs + incremental,
  per decision #6).
- Modern content format (future effort; noted where it intersects).
- Player-save format changes — player JSON saves stay as-is for now, so
  existing rom24 test characters keep working. Format modernization rides with
  the future content-format effort.
- Area *editing* (OLC or the planned DearPyGui editor in the kbk repo).

---

## Section 1 — Boot & persistence redesign ✅ approved

The engine stops persisting world state entirely.

**Deleted:**
- `database/write_tables.py` and the instance tracker — no serialization of
  mobs/objects/rooms to `data/world/instances/`.
- `database/read_tables.py` and all `src/data/*.json` game tables.
- `instance.save()` at boot, `init_instance()` disk loading, and the
  `WORLD_DIR`/`INSTANCE_DIR` settings.
- The pickle legacy-load path (`uait/legacy_loads.py`, `do_apickle`).

**New boot sequence:**
`init_time()` → import content package (tables land in memory) → parse `.are`
files into in-memory prototypes → run area resets to populate the world → wire
exits. Every restart rebuilds the world pristine from flat files; nothing
world-related is ever written to disk.

**Still persists (format unchanged):**
- **Players** — existing per-player save (including inventory instances),
  written on save/quit as today.
- **System files** — bans, notes, bugs/typos, and KBK's operational ledgers
  (`bounties.txt`, cabal-items tracking) under `SYSTEM_DIR`.

## Section 2 — Content package, Python tables, converter ✅ approved (rev 2: profiles dropped)

KBK's tables live as generated Python modules in a single content package;
stock ROM's JSON tables and 52 stock areas are **removed**:

```
src/rom24/content/        # GENERATED by tools/kbk_import.py — do not hand-edit
    classes.py  races.py  skills.py  groups.py  materials.py  __init__.py
src/area/                 # KBK's 100 .are files + area.lst (copied by converter)
```

Boot imports `content`, which populates the same in-memory registries the
engine already uses (`const.skill_table`, `guild_table`, `race_table`, …) —
the same pattern the 97 existing spell modules use via
`const.register_spell()`. No parsing, no JSON — just imports.

**Table shape extensions:**
- `guild_type` gains `align`, `xpadd`, `ctype` (class category), and multiple
  guild rooms.
- `pc_race_type` needs no new fields: KBK's per-class allowed/restricted array
  maps onto the existing `class_mult` field (0 = class not allowed), and KBK's
  racial ability lists, stat caps, and size map onto the existing `skills`,
  `max_stats`, and `size` fields.
- Skills keep per-class level/rating dicts keyed by class *name*; the engine
  drops any remaining hardcoded 4-class assumptions (mandatory now that the
  stock classes are gone).

**Converter** — `tools/kbk_import.py`, run via
`make import-kbk KBK=~/Development/kbk`:
- Parses `const.c` (class_table, race_table, pc_race_table, skill_table,
  group_table) and `area/materials.lst`.
- Emits `content/*.py` with a `# GENERATED — do not hand-edit` header;
  every re-import is reviewable as a plain git diff.
- Copies `area/*.are` + `area.lst` into `src/area/`.
- Wires spells by name-match to the ~97 Python spell implementations rom24
  already has; everything else gets `spell_fun=None`.

**Unimplemented-spell stub behavior:** entries with `spell_fun=None` exist as
data — listed, practicable, grantable by groups — but casting produces a
graceful "that magic hasn't been rewoven yet" message, consumes no mana, and
never crashes. Implementing a spell later = writing its Python function; no
table changes.

## Section 3 — KBK area format support (in review)

96 of KBK's 100 areas use the Tartarus OLC format (`#AREADATA`, `#MOBDATA`,
`#OBJDATA`, `#ROOMDATA`, `#RESETS`, `#SHOPS`, `#SPECIALS`, `#IMPROGS`); the
rest are special files (`help.are`, `social.are`, `social2.are`) using legacy
`#HELPS`/`#SOCIALS` sections.

- **One section dispatcher.** `data_loader` routes each `#SECTION` header to a
  handler. New OLC handlers are written by mirroring KBK's C loaders
  (`db.c`/`db2.c`) field-for-field — the C code is the format's ground truth.
  Legacy handlers stay for the sections KBK still uses (`#HELPS`, `#SOCIALS`);
  dead legacy handlers can be pruned once the stock areas are gone.
- **`#IMPROGS` parse into prog bindings.** Each entry binds a named prog +
  trigger to a mob/object/room prototype, feeding the prog framework
  (section 5).
- **Extended flags & materials.** KBK's 24-flag imm/res/vuln sets and material
  names resolve through the generated tables. Anything unrecognized logs a
  warning and is skipped — boot never crashes on bad content. The loader emits
  a boot summary of warts (dangling vnums, unknown flags) instead of dying.
- **Color codes pass through.** KBK text keeps its `{R}`-style codes in data;
  they translate to ANSI at the output layer via existing miniboa color
  support so players don't see literal `{R}`.

## Section 4 — Engine touchpoints, error handling, testing (in review)

**Character creation (`nanny.py`):** must offer KBK's 13 classes and 24
playable races from the in-memory tables (it largely reads tables already).
Alignment restrictions and race class-restrictions from the KBK data are
enforced at creation. Race special-ability *lists* are granted as skills
(inert if unimplemented, per the stub policy).

**Level/skill constants:** both games use `MAX_LEVEL=60`; KBK's
`skill_adept=75`, per-class values, and immortal-level titles (Hero 51 →
Implementor 60) come from the tables, not constants.

**Error-handling policy (boot):** parse errors in an area file abort *that
file* with a logged error, not the boot; unknown flags/materials/vnums log
warnings; the boot ends with a summary line (`100 areas, N warnings, 0 errors`).

**Testing** (pytest; CI workflow already exists):
- Converter unit tests: known `const.c` snippets → expected table entries.
- Area-parser tests: each OLC section handler against real KBK area excerpts.
- Full-load test: all 100 KBK areas parse without error.
- Boot smoke test — boots, world populated, no world files written to disk
  (asserts the persistence removal).
- Stub-cast test: casting an unimplemented spell fizzles without exception.
- System tests: cabal membership, bounty credit flow, prog trigger dispatch
  (section 5).

## Section 5 — KBK systems: cabals, bounties, quests, progs (new — in review)

**Prog framework (IPROG/MPROG/RPROG).** In KBK these are *named C functions*
dispatched on triggers (mob: attack/bribe/entry/greet/give/fight/death/pulse/
speech/move/request; item: wear/remove/get/drop/sacrifice/invoke; room:
speech/entry), bound to prototypes via the `#IMPROGS` area sections. The port:
- A trigger dispatch layer hooked into the engine's existing event points
  (rom24's `pyprogs.py` event system is the natural home), firing bound progs
  at the same points the C mud does.
- Each named C prog becomes a Python function in a prog registry
  (`rom24/progs/`), looked up by name — exactly like spell registration.
- The converter inventories every prog name referenced by the 100 areas;
  load-bearing progs (cabal guardians, key area mechanics) are ported in this
  effort. A referenced-but-unported prog logs once at boot and is inert at
  runtime — same graceful-degradation policy as spells.

**Cabals** (from `morecabal.c`): the 9 cabals with membership on the
character, cabal items with tracked ownership (`citems.txt` in `SYSTEM_DIR`),
inner/outer guardian mobs (via act flags + progs), cabal recall rooms, and
the cabal-related commands. Quest credits field on PC data.

**Bounty system** (from `bounty.c`): bounty credits per player, bounty ranks,
placing/collecting bounties, ledger persisted to `bounties.txt` in
`SYSTEM_DIR` (consistent with the persistence line — it's an operational
system file, not world state).

**Quest store** (from `queststore.c`): quest credits earned through combat,
per-class reward redemption commands.

**Mob specials** (`special.c`): KBK's spec_fun set (e.g. `spec_monk`, healers,
guardians) inventoried and ported into rom24's existing `special.py` registry;
unknown spec names log-and-inert.

## Acceptance criteria

1. rom24 boots as KBK: 100 areas load, resets populate mobs/objects, telnet
   login works, a new character can pick any of the 13 classes / 24 races and
   play.
2. Cabal membership/items/guardians, bounty placement/collection, and quest
   credits work; prog triggers fire for ported progs; unported progs/spells
   degrade gracefully (logged, inert, no crash).
3. No `src/data/*.json` game tables remain; nothing is written under
   `data/world/`; a restart yields a pristine world while players and system
   files (incl. `bounties.txt`, cabal items) persist.
4. `make import-kbk` regenerates `content/` + `area/` from a kbk checkout,
   idempotently (clean re-run → empty git diff).
5. Test suite covering the above passes in CI.

## Later phases of this project (after the phases above)

- Python implementations for the long tail of KBK-specific spells/skills and
  remaining progs — worked through incrementally behind the stub policy until
  **full parity: KBK runs entirely on the Python framework**, which is the
  project's definition of done.

## Future work (separate efforts, not this project)

- Modern content format for areas/tables/player saves (stated end goal) — the
  converter and single-dispatch loader are built so this slots in as "one more
  emit target / one more loader" later.
- Area editor integration (kbk repo's DearPyGui editor plans).
